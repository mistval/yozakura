The prompt template system controls the wording used for prompts, and the dynamic scenario state information that's injected into prompts. The template system is very flexible and has access to practically the entire scenario state. On the other hand, it's a pain to read and write. The suggested workflow is to have a frontier LLM do significant changes for you.

## Accessing templates

Go to the settings cog -> Prompt Templates -> drill down to find the one you want.

## The Robot Button

Each group of related prompts has a robot button in the top right corner. Click it and it generates a context document for consumption by an AI assistant. Copy it to your AI of choice, tell it what changes you want, and follow its instructions. Modern frontier LLMs tend to be very good at this.

### Example

Me:

```md
Hey AI, read this big document I'm uploading and explain this prompt to me simply. <attaches chat system prompt document from robot button>
```

AI:

```md
This document is for a tool called **Yozakura**, an AI-powered social simulation. Think of it like a little virtual world where AI characters walk around a map, bump into each other, and have conversations — each character's dialogue is generated by an LLM. After they talk, the system updates their "memories" of each other.

The document is showing you the _prompts_ that get sent to the LLM to make a character speak, and it's asking you (well, me) to help edit them. Here's what each piece does.

**The Chat System Prompt** is the main one. Every time a character needs to say something, this template assembles a fresh set of instructions for the AI by stitching together everything the character "knows" in that moment:

- Whether they're in a one-on-one chat or a group chat, and who with
- Who they're supposed to be (the character's persona, their writing style via example dialogue, and their personal goals/memories)
- What this character remembers about each other person in the conversation
- A goal they might want to bring up (in one-on-one chats)
- The setting — the world description and where they currently are
- Optionally, "gossip": a character who _isn't_ present that the system nudges them to maybe mention
- House rules at the end: write in first person, keep it to three sentences, use quotes for speech and asterisks for actions/thoughts, don't repeat yourself

The clever bit is that it's rebuilt for _every_ message, so it stays current as the conversation evolves.

**The Final Instructions Prompt** is a shorter reminder tacked on at the very end, right before the AI replies. It restates the key rules (write the next line, be concise, formatting style, no repetition) so they're fresh in the model's "mind" at the moment of generation. It also adapts slightly — if it's a text-message chat rather than an in-person conversation, it tells the AI to write in casual texting style with emojis.

**The Parser** is the simplest part. After the AI writes its response, a parser can transform the text — but here it just returns it unchanged (`response => response`), because no special processing is needed.

The rest of the document (that giant schema) is just reference material listing _all_ the data the templates are allowed to pull from — characters, locations, relationships, conversation history, and so on.

What would you like to change? If you tell me the behavior you're after, I can edit the right template for you.
```

Me:

```md
Can you make it so the characters know who else is in the same room as them (but not in the conversation)? Also if possible, include the relationship status (the short one, like "friend", etc).
```

AI:

```md
Good news: everything you need is already in the context object, so this is doable. There's a `currentLocation` plus every character's `locationId`, which lets me find who's physically present, and `getRelationship(...)` returns a short `descriptor` field (exactly the "friend" / "rival" style label you want).

You only need to update **one** UI element: the **Chat System Prompt** textarea. The Final Instructions Prompt and Parser stay as they are.

Here's the full updated template — I added one new block right after the `<setting>` section:

`<updated template>`

A few notes on the choices I made:

The new block finds everyone whose `locationId` matches the focused character's location, then removes the character themselves, anyone already in the conversation, and the gossip target (so they don't get listed twice). Each remaining person is shown with their short relationship descriptor in parentheses, e.g. `Bob Smith (friend)`. If the character hasn't met them, `getRelationship` won't return a descriptor, so it falls back to `(a stranger to <Name>)` — tweak that wording to taste, or change it to just show the name if you'd rather.

One thing worth knowing: in a `remote` (texting) chat, `currentLocation` is only the _focused_ character's location, so this block will list whoever is physically standing near the speaker while they text — not the people they're texting with. That's usually the sensible behavior, but flag it if you intended something different and I can adjust.
```

### Example 2

Me:

```
Hey AI,  based on these instructions, would it be possible to include the current weather at my actual location (zip code XXXXX)?
```

Perhaps surprisingly, the answer is yes!

AI:

```md
Yes, this is doable. The template runs in the browser with `fetch` and `await` available, so I can pull live weather inside the Chat System Prompt template. A few design choices worth flagging:

- I'm using **Open-Meteo**, since it's free, needs no API key, and (importantly) sends CORS headers — so you shouldn't need a proxy. It takes lat/long rather than a zip, so I hardcoded the coordinates for XXXXX. They're labeled at the top of the block so you can change them later.
- That system prompt is **re-rendered on every message**, so to avoid hammering the API I cache the result in `globalWritableContext` and only refetch every 30 minutes.
- If the fetch fails for any reason, it silently omits the weather rather than breaking the whole prompt.

You only need to update **one UI element: the "Chat System Prompt" textarea.** No parser change is needed (weather goes into the prompt, not the output). Replace its entire contents with this:

`<updated template with external weather API call>`

A couple of caveats:

The weather reflects your _real_ location, which won't necessarily match the simulation's fictional world/location — that's why I labeled it explicitly as "real-world weather" so the model treats it as ambient flavor rather than assuming the map is actually in your city. If you'd rather have it silently color the scene (e.g. "it's raining" influencing mood without the characters naming a zip code), reword the line inside `<setting>` however you like; the `weatherText` variable is the only part that matters.

If Open-Meteo ever stops working from your browser (CORS or downtime), the block just drops the weather line silently. In that unlikely case you'd wrap the URL in a CORS proxy, but you almost certainly won't need to with this provider.
```

## Format

Yozakura prompts are rendered by [Eta](https://www.npmjs.com/package/eta) which is essentially equivalent to [EJS](https://www.npmjs.com/package/ejs) except faster. All EJS syntax is supported, and `await` is also supported inside of templates.

## Validation Checklist After Template Edits

1. Context objects still satisfy each chain's `contextSchema`.
2. Parser output still matches parser schema for that chain.
3. Changes only affect the intended chain(s).
4. One real scenario run completes without parser/runtime errors.
5. Context schema docs are regenerated when schemas change.

For hands-on editing guidance, see [Template Editing Instructions](./template-editing-instructions.md).
